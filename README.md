## Branch and Commit Specifications
In this section, we introduce the branches and commits.

### Branch Descriptions
* **`main` branch**: The main branch of the project, which always contains stable, tested code that is ready for the Production environment.
* **`dev` branch**: The main development branch where all new features are initially merged and tested for deployment, and are eventually merged into `main`.
* **`feature` branch**: A branch created for developing a new feature or functionality in the project.
* **`hotfix` branch**: An emergency branch created to quickly fix bugs in the existing code.
* **`architecture` branch**: A dedicated branch used for implementing, modifying, or improving the basic structure and architecture of the project.
* **`gh-pages` branch**: A special branch that is automatically used for hosting and displaying the frontend output or project documentation through GitHub Pages.
* **`report` branch**: A special branch used for recording and completing the project report.

## Answers to the Experiment Questions

In this section, the questions presented in the experiment are answered.

---

### 1. What is the `.git` directory? What information is stored in it? Which command creates it?
The `.git` directory is the main part of a Git repository. This directory is hidden and located at the root of the project, and it stores the complete history of changes, configurations, and metadata related to the version control of the project.
* **What information is stored in it?** The complete commit history, information related to branches, tags, the `HEAD` pointer (which indicates which branch or commit we are currently on), local repository settings (`Config`), and temporary files related to the Stage.
* **Which command creates it?** This directory is created (initialized) by running the following command in the project directory:
    ```bash
    git init
    ```

---

### 2. What does atomic mean in an atomic commit and an atomic pull request?
The concept of **Atomic** means indivisible. In other words, an operation is either completed entirely or not performed at all, and it cannot be divided into smaller independent parts.
* **Atomic Commit:** Each commit should contain only **one specific, logical, and independent change** (for example, fixing a specific bug or adding a specific feature). If your commit simultaneously fixes a bug and changes the appearance of the website, it is not atomic. Atomic commits improve the readability of the history and make reverting changes much easier if a problem occurs.
* **Atomic Pull Request:** A PR should implement exactly one specific goal or feature. Reviewing a small and atomic PR is much faster and less error-prone for team members than reviewing a huge PR containing several unrelated changes.

---

### 3. Differences between fetch, pull, merge, rebase, and cherry-pick
These commands are all used for managing and integrating changes in Git, but they behave differently:
* **`git fetch`:** Downloads the latest changes from the remote repository and stores them on your system, but it does **not** merge them with your current code. It only updates the list of changes.
* **`git pull`:** A combination of the `fetch` and `merge` commands. It first retrieves the changes from the remote repository and immediately merges them into your current branch.
* **`git merge`:** Merges two branches together. This command creates a new commit called a **Merge Commit**, which preserves the history of both branches. In this case, the history is displayed in a branched (non-linear) form.
* **`git rebase`:** Moves the base of your current branch to the latest commit of another branch. This causes all of your commits to be rewritten and placed after the commits of the new base branch. The result is a completely **linear and clean** history.
* **`git cherry-pick`:** Allows you to select **only one specific commit** from another branch and apply the changes from that single commit to your current branch, without needing to merge the entire branch.

---

### 4. Differences between reset, revert, restore, switch, and checkout
These commands are used for navigating through history or managing files:
* **`git reset`:** Used to move the branch state back to a specific commit. This command modifies history and, depending on the flags (`--soft`, `--mixed`, `--hard`), can either preserve or completely remove the changes from later commits.
* **`git revert`:** Creates a new commit that applies the exact opposite of the changes made by an older commit. This command does not delete previous history, so it is much safer than `reset` for online and shared repositories.
* **`git restore`:** Used to restore files in the Working Directory or Staging Area to their last saved state without modifying commits.
* **`git switch`:** A dedicated command used only for switching between branches, introduced to remove the ambiguities of the older `checkout` command.
* **`git checkout`:** An older multi-purpose command. It can be used for switching between branches, moving to a specific commit, and restoring files to a previous state.

---

### 5. What is the stage, also known as the index? What does the stash command do?
* **Stage (Index):** A preparation or draft area between your Working Directory and the Git Repository. When you modify a file and run the `git add` command, the file is moved to the Stage. Git only commits changes that have first been added to this area.
* **`git stash`:** This command is useful when you have made changes to the code but your work is not yet complete and you want to temporarily switch branches or perform an urgent task. The `stash` command safely and temporarily stores (hides) your uncommitted changes and cleans your working directory. Later, you can restore those changes using the `git stash pop` command.

---

### 6. What does snapshot mean? What is its relationship with a commit?
* **Snapshot:** This means that at any moment, Git records an overall view of all project files and their contents. If a file has not changed, Git does not store it again and instead creates a link to the previous file.
* **Relationship with Commit:** Every commit in Git is actually a **Snapshot** of the entire project at that specific moment in time, bundled and stored together with metadata such as the author name, commit message, timestamp, and unique Hash.

---

### 7. Differences between a local repository and a remote repository
Git is a **Distributed** version control system, which means that the repository exists in multiple locations:
* **Local Repository:** A repository located on your personal computer (the same `.git` directory). You can commit, create branches, and inspect the history without needing an internet connection. Changes in this repository are not visible to others until they are pushed.
* **Remote Repository:** A repository hosted on a server, such as GitHub or GitLab. This repository acts as the main shared source among team members. Team members `push` their local changes to this repository and retrieve other people's changes from it using `pull` or `fetch`.

## پاسخ به سوالات آزمایش

در این بخش به سوالات مطرح شده در آزمایش پاسخ داده شده است.

---

### ۱. پوشه‌ی `.git` چیست؟ چه اطلاعاتی در آن ذخیره می‌شود؟ با چه دستوری ساخته می‌شود؟
پوشه `.git` قسمت اصلی یک مخزن (Repository) در گیت است. این پوشه به صورت مخفی در root پروژه قرار دارد و تمام تاریخچه تغییرات، تنظیمات و متا‌دیتاهای مربوط به مدیریت نسخه پروژه را در خود نگه می‌دارد.
* **چه اطلاعاتی در آن ذخیره می‌شود؟** تاریخچه کامل کامیت‌ها (Commits)، اطلاعات مربوط به برنچ‌ها (Branches)، تگ‌ها (Tags)، پوینتر `HEAD` (که نشان می‌دهد الان روی کدام برنچ یا کامیت هستیم)، تنظیمات محلی مخزن (Config) و فایل‌های موقت مربوط به Stage.
* **با چه دستوری ساخته می‌شود؟** این پوشه با اجرای دستور زیر در مسیر پروژه ساخته (مقداردهی اولیه) می‌شود:
    ```bash
    git init
    ```

---

### ۲. منظور از atomic بودن در atomic commit و atomic pull-request چیست؟
مفهوم **Atomic** به معنای تفکیک‌ناپذیر بودن است. به بیان دیگر یعنی یک کار یا به طور کامل انجام می‌شود یا اصلاً انجام نمی‌شود و نمی‌توان آن را به بخش‌های کوچک‌ترِ مستقل تقسیم کرد.
* مفهوم **Atomic Commit:** یعنی هر کامیت باید فقط و فقط شامل **یک تغییر مشخص، منطقی و مستقل** باشد (مثلاً رفع یک باگ خاص یا اضافه کردن یک ویژگی مشخص). اگر کامیت شما همزمان یک باگ را رفع کند و ظاهر سایت را هم تغییر دهد، اتمی نیست. کامیت‌های اتمی خوانایی تاریخچه را بالا برده و در صورت بروز مشکل، بازگردانی (Revert) آن‌ها را بسیار آسان می‌کنند.
* مفهوم **Atomic Pull-Request:** یعنی یک PR باید دقیقاً یک هدف یا ویژگی مشخص را پیاده‌سازی کند. Review کردن یک PR کوچک و اتمی برای اعضای تیم بسیار سریع‌تر و کم‌خطاتر از یک PR غول‌آسا با چندین تغییر بی‌ربط است.

---

### ۳. تفاوت دستورهای fetch ،pull ،merge ،rebase و cherry-pick
این دستورها همگی برای مدیریت و ادغام تغییرات در گیت استفاده می‌شوند اما رفتارهای متفاوتی دارند:
* دستور **`git fetch`:** آخرین تغییرات را از مخزن آنلاین (Remote) دریافت می‌کند و در سیستم شما قرار می‌دهد، اما آن‌ها را با کد فعلی شما ادغام (Merge) **نمی‌کند**. فقط لیست تغییرات را به‌روز می‌کند.
* دستور **`git pull`:** ترکیبی از دو دستور `fetch` و `merge` است. یعنی ابتدا تغییرات را از ریموت می‌گیرد و بلافاصله آن‌ها را با برنچ فعلی شما ادغام می‌کند.
* دستور **`git merge`:** دو برنچ را با هم ادغام می‌کند. این دستور یک کامیت جدید به نام **Merge Commit** ایجاد می‌کند که تاریخچه هر دو برنچ را حفظ می‌کند. تاریخچه در این حالت به صورت شاخه‌شاخه (غیرخطی) دیده می‌شود.
* دستور **`git rebase`:** بیس یا پایه برنچ فعلی شما را به آخرین کامیت برنچ دیگر منتقل می‌کند. این کار باعث می‌شود تمام کامیت‌های شما بازنویسی شده و پشت سر کامیت‌های برنچ جدید قرار بگیرند. نتیجه این دستور یک تاریخچه کاملاً **خطی و تمیز** است.
* دستور **`git cherry-pick`:** به شما اجازه می‌دهد **فقط یک کامیت خاص** را از یک برنچ دیگر انتخاب کنید و تغییرات همان یک کامیت را روی برنچ فعلی خود اعمال کنید (بدون نیاز به ادغام کل برنچ).

---

### ۴. تفاوت دستورهای reset ،revert ،restore ،switch و checkout
این دستورها برای جابجایی در تاریخچه یا مدیریت فایل‌ها استفاده می‌شوند:
* دستور **`git reset`:** برای به عقب بردن وضعیت برنچ به یک کامیت خاص استفاده می‌شود. این دستور تاریخچه را دستکاری می‌کند و بسته به flag ها (`--soft`, `--mixed`, `--hard`) می‌تواند تغییرات کامیت‌های بعدی را نگه دارد یا کاملاً پاک کند.
* دستور **`git revert`:** یک کامیت جدید ایجاد می‌کند که دقیقاً عکس تغییرات یک کامیت قدیمی را اعمال می‌کند. این دستور تاریخچه گذشته را پاک نمی‌کند، بنابراین برای مخازن آنلاین و اشتراکی بسیار امن‌تر از `reset` است.
* دستور **`git restore`:** برای بازگرداندن فایل‌های موجود در Working Directory یا Staging Area به آخرین وضعیت ذخیره شده (بدون دستکاری کامیت‌ها) استفاده می‌شود.
* دستور **`git switch`:** یک دستور اختصاصی است که صرفاً برای جابجا شدن بین برنچ‌هااستفاده می‌شود تا ابهامات دستور قدیمی checkout برطرف شود.
* دستور **`git checkout`:** یک دستور چندکاره و قدیمی است. هم برای switch کردن بین برنچ‌ها، هم برای رفتن به یک کامیت خاص و هم برای بازگرداندن فایل‌ها به وضعیت گذشته استفاده می‌شود.

---

### ۵. منظور از stage یا همان index چیست؟ دستور stash چه کاری انجام می‌دهد؟
* منظور **Stage (Index):** یک فضای آماده‌سازی یا پیش‌نویس بین پوشه کاری شما (Working Directory) و تاریخچه گیت (Repository) است. وقتی فایلی را تغییر می‌دهید و دستور `git add` را می‌زنید، فایل به محیط Stage می‌رود. گیت فقط تغییراتی را کامیت می‌کند که ابتدا به این محیط اضافه شده باشند.
* دستور **`git stash`:** زمانی کاربرد دارد که شما تغییراتی در کد داده‌اید اما کارتان هنوز تمام نشده و می‌خواهید موقتاً برنچ خود را عوض کنید یا یک کار فوری انجام دهید. دستور `stash` تغییرات کامیت‌نشده شما را در یک فضای امن و موقت ذخیره (پنهان) کرده و پوشه کاری شما را تمیز می‌کند. بعداً می‌توانید با دستور `git stash pop` آن تغییرات را دوباره برگردانید.

---

### ۶. مفهوم snapshot به چه معناست؟ ارتباط آن با commit چیست؟
* **مفهوم Snapshot:** یعنی گیت در هر لحظه، نمایی کلی از تمام فایل‌های پروژه و محتوای آن‌ها را ثبت می‌کند. اگر فایلی تغییر نکرده باشد، گیت دوباره آن را ذخیره نمی‌کند، بلکه فقط یک لینک به فایل قبلی ایجاد می‌کند.
* **ارتباط با Commit:** هر کامیت در گیت، در واقع یک **Snapshot** از کل پروژه در همان لحظه زمانی مشخص است که با متادیتاهایی مثل نام نویسنده، پیام کامیت، زمان ثبت و هَش (Hash) اختصاصی باندل و ذخیره شده است.

---

### ۷. تفاوت‌های local repository و remote repository
گیت یک سیستم کنترل نسخه **توزیع‌شده (Distributed)** است، به این معنی که مخزن در چندین مکان وجود دارد:
* مخزن محلی **Local Repository:** مخزنی است که روی کامپیوتر شخص شما قرار دارد (همان پوشه `.git`). شما بدون نیاز به اینترنت می‌توانید در آن کامیت کنید، برنچ بسازید و تاریخچه را بررسی کنید. تغییرات این مخزن تا زمانی که Push نشوند، برای دیگران قابل مشاهده نیستند.
* مخزن آنلاین**Remote Repository:** مخزنی است که روی یک سرور میزبانی می‌شود (مثل GitHub یا GitLab). این مخزن به عنوان منبع اصلی و مشترک بین اعضای تیم عمل می‌کند. اعضای تیم تغییرات محلی خود را به این مخزن `push` می‌کنند و تغییرات دیگران را از آن `pull` یا `fetch` می‌کنند.
